Application overview

The purpose of MasterClaw eoLive is to support tasks of first and second level Service Management Centre (SMC) personnel in the context of monitoring telecommunication networks and services in wireless and fixed-line domains. These include wireless (e.g., GSM/GPRS/UMTS) access and core networks, fixed-line services (Voice, VoIP, broadband access, IPTV etc.), as well as convergent services (e.g., based on IMS).

The application provides statistics based on transaction records. Statistics based on transaction records provide information on subscriber related activities. For example, call transaction record provides information on the calling and called party, release causes, call duration, called operator, etc. The application provides the possibility to create statistics based on transaction records and freely set filtering conditions. For example, it is possible to count the number of extra-long calls that are directed towards certain Operators (to follow up on a possible fraud case).

Application architecture

The overall eoLive architecture is depicted in the following f igure :

Top level components

  • Probe: the scope of this component is to collect protocol messages from the network and to produce CSDRs
  • Data Gateway Server : the scope of this component is to collect CSDRs from the probe, correlate them, and aggregate data based on the KPI defined in eoLive UI. See Reference documents.
  • Configuration Database (CDB): the purpose of this component is to store network configurations, KPI configurations, format definitions and Data Gateway instance configurations.
  • eoLive Server: this component acts as an intermediary between eoLive User Interface (UI), Data Gateway server, and Central Database, thus performing the following tasks:
    • Collecting data from different Data Gateway servers configured in the network
    • Storing KPIs into the eoLive server database
    • Storing the KPI configuration, defined in the eoLive UI, into the Central Database
    • Providing network topology info during KPI configuration
    • Providing eoLive UI with real-time KPIs
    • Providing eoLive UI with historical KPIs when requested by them
  • eoLive User Interface: The purpose of this component is to:
    • Configure KPIs, charts and alarms
    • Create, delete, and organize charts in public and private data views
    • Show real-time KPIs and historical data
    • Jump to detailed data record
  • eoSearch Client : the purpose of this component is showing raw data record stored in eoSearch Browse database, and showing call trace. See Reference documents.
  • eoSearch Browse : the purpose of this component is to browse the data records (eoDRs) produced by the Data Record Gateway (aka QXDRS) and stored in NDAF. See Reference documents.
  • NDAF Elasticsearch: if this component is installed with live-srv, it will be used to store information for chart definitions, kpi values, and alarms that will be used in advanced searches.

Getting started

This chapter guides you through the steps necessary to start using eoLive User Interface. These include making sure the necessary software is installed on your workstation, getting a user account with the right capabilities, and launching the application.

Prerequisites

As already mentioned, the application runs in a web browser, so the user needs one web browser installed on their workstation or tablet. The supported browsers are listed in the Technical Baseline for Clients (see Reference documents).

In order to access the application, you as the user need to be a member of one or more user groups with at least the following capabilities:

  • Portal

    Needed to log in to the Portal

  • eoLive

The capability required to start eoLive User Interface

There are other capabilities that give permission to create, edit, and delete objects, and to see information related to the configuration of parts of the monitored network. For the other capabilities, see User profiles and capabilities.

Starting eoLive

Start the application by clicking on the relevant card in the Portal Analysis tab. If you have all the necessary capabilities, the application will open in the same browser window and tab.

For more information about how to launch applications, see the corresponding chapter in Portal Operator Manual (see Reference documents).

Advanced search panel

If ElasticSearch is enabled, the advanced search panel will be available in the main eoLive page.

Advanced Search Panel

  • Toggle button – The advanced search panel is not displayed at start time. This button shows/hides the advanced search panel.
  • Simple search box – This text box will be enabled only when the selected filters list is empty; it will be used to search matches only on text filters for chart definitions.
  • Filters – The list of the available filters:
    • The first filter "Everything" will search the value in the text box in all text filters.
    • KPI value filters: KPI Value, KPI Volume, KPI Managed Object, KPI Drill Object.
    • Alarm filters: Alarm Severity, Alarm Managed Object.
    • Chart definition filters: Chart Input Filter, Chart KPI Expression, Chart Drill Object, Chart Title, Chart Granularity, Chart Type, Chart Value Axis, Chart Scale Type, Chart Group By.

Only "Alarm" and "KPI Value" filters are time-based. These filters will return charts having the main KPI or drills KPIs matching the filters for the selected period of time.

There are two types of filter, "text" and "numeric". The only numeric filters are "KPI Value" and "KPI Volume". For the text filters we search charts by using strings that are contained in the parameter names, according to the selected filter.

For the numeric filters, we search charts with values equals to the filter value if we have a single value or charts with values in the range specified by "Value" and "Range search". The second value must be greater than the first.

The "Add filter" button is enabled only when a valid value for a filter is present.

  • Time Range –a list of predefined periods for time-based filters. Default time range is past 30 minutes. "From" and "To" are visible only for Range option.
  • Selected filters list – contains filters added in the search request. You can remove any filter using the "Remove" button. Selected filters can be grouped in two levels. The first level is available when we have more than 1 filter. You can change the logical condition by clicking on the first level bar. The second level is available when there are more than two filters. In order to add the second level you must select at least two filters from the list and use the buttons above to select the logical condition.
  • Matched chart information – in the Dataview Navigation area, under each Dataview are listed information for the matched charts. Each item is grouped in three columns:
    • The first column contains the chart title and the drill managed object in case the matching corresponds to a drill KPI.
    • The second column contains the matched filter with the managed object for KPI values and alarm filters, as well as the last matched value.
    • The last column shows the last time when the KPI value or alarm filters were matched for that chart.

The purpose of the automatic thresholds is to identify sensitive changes in the KPI trend that rapidly turn into values deemed critical from a business point of view.

eoLive leverages on a low-pass filter algorithm plus a smothering technique to adapt a cut off frequency on the traffic/KPI trend and eventually neglect noisy portions of the shape that causes low but steep variations.

In order to influence the algorithm, eoLive offers some settings to better calculate the cut off frequency and noise attenuation dynamically:

  • Number of Samples: number of KPI values used to calculate an average value which derives through processing to cut off frequency
  • Standard Deviation: amount of dispersion of the data set to influence the steepness of the filter window cut off frequency.

Number of samples

The purpose of this parameter is to make the expected kpi trend uniform, reducing the effect of high or low spikes that suddenly return to normal. Instead, a number of samples equal to 1 decouples the last value from the historical values and the calculated threshold will always be compared with the last value.

The examples below show the effect of the parameter's value in two different cases, having ignored the previous value of the KPI (Number of Samples = 1) and considering the historical values (Number of Samples = 5):

  • In the former case, due to the absence of value at interval 46:15, the computed threshold drops drastically to 0 and, consequently, the intervals marked in the red circle result alarmed
  • In the latter case, the computed threshold results less affected by the absence of value at interval 45:15, holding a value that keeps almost all the following intervals below the safe value.

Standard deviation

This value represents the absolute deviation of the kpi that triggers an alarm: if the current value of KPI does not breach the configured value, the interval does not raise an alarm. Basically, this parameter affects the level of the computed threshold. The following examples show two cases with the parameter's value set to 100 and 5000. Prediction

In this section, the user can choose to see where the KPI trend is heading in the future, based on past values in a chart.

Prediction Tab

The prediction tab has following settings:

  • Enable Prediction: enable or disable KPI trend prediction.

  • Enable Alarm Prediction : enable or disable an alarm based on prediction. This configuration is relevant only if alarms are enabled and defined in the chart (check section Alarms).

    If in the past no alarms were thrown, and it is predicted to have alarms for the incoming predicted values, these predicted alarms will be displayed in the Alarm Manager with "#PREDICTION#" included in the Alarm Name. Once the real data reaches the timestamp of those predicted raised alarms, a clear alarm will be sent .

    In case it is alarm based on real values, and the prediction is that will be again alarm, then the outcoming depends on the alarm type. In case of a pulse alarm, it is sent to Alarm Manager the predicted alarm; in case of state-change alarm, it isn't because the prediction is that the state will not be changed. The same principles follow also with the delta alarms.

    Predicted Alarms in Alarm Manager

    If for each interval, it is predicted, let's say the next 5 intervals where 5 is the number of prediction intervals configured, the alarm will be raised only for the most forward predicted interval, so the user will not have 5 alarms for each predicted interval.

  • Number Of Prediction Intervals: The number of prediction intervals can be seen in the chart. The available range is [1,5], where the default value is 3.

  • Level: This is the smoothing factor for the level component and represents the weight given to the most recent observation in the time series. It represents the degree of adaptation of the level component to new observations and controls the speed of convergence of the forecast to the actual data. A higher value will result in a more responsive model to changes in the data, while a lower value will result in a smoother model with slower convergence. The available range is [0.0, 1.0], where the default value is 0.3.

  • Trend: This is the smoothing factor for the trend component and represents the weight given to the past forecast errors. The forecast errors are the differences between the actual values and the values predicted by the model. The choice of the Trend parameter determines the trade-off between responsiveness to changes in the data and stability of the model. A high value gives more weight to the past forecast errors, causing the model to respond more quickly to changes in the data. A low value gives more weight to the past trend, causing the model to be more stable and less responsive to short-term fluctuations in the data. The available range is [0.0, 1.0], where the default value is 0.1.

  • Seasonality: This is the smoothing factor for the seasonal component and represents the weight given to the seasonal deviations from the mean. It represents the degree of adaptation of the seasonal component to the actual data and controls the sensitivity of the forecast to changes in the seasonality. A higher value will result in a more responsive model to changes in the seasonality, while a lower value will result in a smoother model with slower convergence. The available range is [0.0, 1.0] and the default value is 0.3.

  • Period: The number of time intervals in a complete seasonal pattern. The seasonal pattern is a regular and repeating pattern in the data that occurs over a fixed period of time. For example, for a chart with the main granularity of 5 min, if the user wants to have seasonal pattern that repeats every hour, then the period must be 12. The available range is [1, trend interval of the current granularity] and the default value is 1.

  • Auto fill: Calculates and tries to find the optimal values for Level, Trend, Seasonality, Period variables. After a chart is created it is important to wait a few intervals to collect enough data to calculate the ideal forecast setup. Usually is enough to have collected at least trend interval of data (for example, for granularity of 15 s, the trend interval is 40; for the other granularities, please refer to Presentation – Data record chart). In the worst case, i.e. when the seasonality parameter is equal to the trend interval of the main granularity, it is necessary to wait for twice the trend interval length time.

  • Clear: This button loads the original values for Level, Trend, Seasonality, Period variables, after the Auto Fill button was used.

  • Show Preview: Offers a preview of the chart with the given settings available in this tab.

  • Reload: Reloads the chart with the given setup.

DataView filter

Introduction

eoLive provides post-filtering capabilities at the chart or/and Dataview level by displaying a dialog window after clicking on the "Filters in chart" icon (see Filters in chart/DV). This option is highly functional, but in case the filter is applied to a whole Dataview, it is difficult for the end user to understand which filter is applied to which chart, etc. For this reason, a new type of widget called "Filter widget" has been introduced. It gives to the end user alternative options to configure the filter for particular charts in Dataview (specified by "grouping by field"). Additionally, the filter widget shows the configuration of the filter directly, after opening a specific Dataview in order to provide a contextual help in post-filtering capabilities and speed up troubleshooting analysis.

The Filter widget allows the user to limit the visibility of a managed object in a chart or Dataview. Only the managed objects that meet the expression criteria are visible in the chart. Users are able to specify the filter either by Managed Objects, Managed Object Regex Value and KPI value, or by data volume. This widget is visible in a dedicated panel of the main window of the Dataview and shows the list of possible managed object or KPI limits based on the configuration.

Only users with eoLive admin capabilities are able to create a filter in "Public" folders. Other users are able to create filters in their own "Private" Dataview. Another option is to edit the filter "on the fly" – that is, directly selecting/unselecting MO values, changing measures by clicking on the filter widget page (not in configuration mode). Please note that this modification is visible only for the current user and is permanent only if filter preferences are turned on, otherwise all these changes will be lost after refreshing the page.

Enhanced security

Restrict access to Dataview/folders

Security model in eoLive provides the means for fine-tuning the read/write access grants up to the single Dataview/folder level, for users and user groups.

This is managed in the User Administration application used by the administrator to customize permissions.

The security model applies only to public Folders/Dataviews. All the private data are accessible only by the owner and the administrators.

By default, the security model principle is that if nothing is configured in security, the resource is public and accessible. As soon as the administrator creates a configuration entity for Folder or Dataview, the enforcement will be applied by eoLive.

Folders' permissions are hierarchical, and the nearest path is considered: for example, eoLive checking permissions on the folder "/public/LTE/test" dataview1 will firstly check if there is a specific resource for DATAVIEW "/public/LTE/test/dataview1", then it will check permissions on the folder "/public/LTE/test"; if it does not exist as resource, it will check "/public/LTE", and so on. If nothing is found, there will be no restrictions.

To allow the access to a resource after its creation, the resource needs to be assigned to a User Group and must also have the following capabilities to control the access level:

  • ViewEoLiveResource
  • ChangeEoLiveResource

Restrict access to data sources

Similarly to how the resources are defined (see section above Restrict access to Dataview/folders), the resources for data sources (DR_FORMAT) can be defined (e.g., eoGB, eoGB-6.0, eoLTE-3.0). The resource ID can be created with or without the version number, to increase its flexibility.

To allow the access to a resource after its creation, the resource needs to be assigned to a User Group and must also have the following capability to control the access level:

  • ViewEoLiveResource

If the user is denied access, the chart will be hidden. This restriction is applied also to charts from dataviews from private (personal) folder.

note

i f access to a data source is restricted, any multiple KPIs chart using this source will not be displayed at all.

Standard MC security capabilities

eoLive is compliant with MC security capabilities, which are used to mask sensitive data such as subscribers' numbers (e.g. IMSI, MSISDN,IMEI), or to mask end point details such as fully qualified point code fields, (e.g. OPC, DPC), etc from charts inside public or private dataviews.

Troubleshooting

This chapter provides practical suggestions to increase the number of available charts while optimizing the internal system performances.

The MasterClaw Aggregator receives single transactions as Data Records and pushes to eoLive Server aggregated data, based on the charts configuration.

For each defined granularity (15 seconds, 1 minutes, 5 minutes, 15 minutes, 30 minutes, 1 hour, 1 day), it pushes the calculated data.

Data records are filtered (Input Filter), then aggregated by the dimension specified in the configuration (Grouping Rule). Up to 5 drills may be defined for additional dimensions; for each drill, the same logic of grouping values is applied.

Apply ranking as much as possible

The Data Record Format enforces restrictions on dimensions that may grow indefinitely (e.g. "Partial URL" because they are based on the traffic), or that are estimated to be very large (e.g. "Cell" because they may have more than 50.000 different values). Most of the Data Records Fields have instead a fixed cardinality (e.g. "Release Cause" has a fixed number of causes).

Nonetheless, some dimensions are not restricted (e.g. Originating Point Codes), on the assumption that the Customer's signaling points have few hundred elements.

The ranking limit ensures that only the N elements are pushed to eoLive. Without ranking, the amount of data received may grow up to 20.000 values at every interval, affecting the time to complete the ingestion.

This is a critical configuration point, especially when the granularity is very low (15 seconds): receiving thousands of elements every 15 seconds would need to be justified by a real use case.

Specify a drill only when it's really needed

When a drill is defined, for each managed object the Aggregator "splits" a value into its subparts. The amount of data required for a drill is, therefore, the product of {No of Managed Objects} X {No of Drill Managed Objects}.

As an example, a formula calculating the number of failures grouped by top 100 Cells with a drill to release causes forces the aggregator to calculate and push, for each Cell, the KPI calculated on each cause. One hundred Cells and 10 different causes may push up to one thousand results every 15 seconds.

Each drill requires a separate KPI and impacts the overall amount of data moved and stored into the single eoLive Server. As such, it shall be used with care.

Use higher granularities if possible

By default, eoLive aggregates by 15 seconds, allowing a very fast response. However, sometimes such low granularities are not required and potentially harmful.

If the KPI is intended to raise alarms, the observation period of 15 seconds may be too low and volatile. A 1-minute or 5-minute interval may provide less fluctuating results, with the additional advantage of sending and storing fewer data into eoLive.

Remove or disable unused charts

eoLive allows for the creation of Dataviews and plays with live data. As powerful as this feature is, it requires a certain amount of care to remove unnecessary charts and Dataviews, which would otherwise be aggregated, pushed, and stored in the system.

After the evaluation period, a chart will either be promoted to a definitive one or removed from the system.

eoLive reuses KPIs if you duplicate a chart. If the duplicated chart is however modified (ranking, dimensions, drills, formulas), then a new, separate KPI will be created to adapt to the different setup.

Disabling a chart has the same impact: when disabled, the KPI will not be calculated by the aggregator and no data will be stored, while preserving the chart configuration.

For this purpose, the "Kpi aging" functionality is helpful, as it automatically detects such dataviews and disables charts therein (for more info see Aging mechanism for Dataviews).

Evaluate the use case

The best optimization is, of course, to have no chart at all if it is not useful.

When creating a new chart, you should consider if:

  • The same chart already exists
  • A similar chart may be expanded to include the use case
  • It covers a real use case.

Avoid long filters

When an input filter condition leverages inlist/not-inlist operators, and the number of values exceeds a hundred values, it could cause performance issues on the aggregator.

If MasterClaw Lookup Service (MCLS) is available, the preferable and best-performing approach to filter data records is based on Enriched Data Record Fields.

Narrow filters for KPI values and alarms on advanced search tab

On the advanced search tab, if the selected filters' list contains only time-based filters with a very large range of values, the result list may be less relevant. If the selected period is wide, the search time will be longer because of the large amount of data to be processed.

tip

try restricting the values by selecting also a chart definition property; in this case, the search for KPI values and alarms will be executed only on a subset of the available KPIs.

KPI Performance Introspection

Network Operations Specialists and Administrators struggle to assess traffic distribution, KPI cardinality, and the criticality of KPIs during their creation or editing. As a result, poorly configured KPIs can lead to performance degradation, traffic imbalances, and operational inefficiencies.

The KPI Introspection and Performance fixture introduces a warnings to enhance visibility and control over KPI configurations and their impact on system performance. By providing real-time introspection scores, cardinality analysis, and criticality tagging during KPI creation, these warning empowers users to make informed decisions that prevent system overload and traffic imbalance.

Features:

  • Real-time introspection after KPI creation.
  • Cardinality analysis with performance impact warnings.
  • Displaying introspection scores in CLI-based reports.
  • Critical KPI tagging during usage.

Main kpi introspection warning

Warning is present for the mainKpi in the Input Filter sections and for drills inside the Drill Option section

Warning limit output

The number of KPI warnings is limited to a maximum of 3 for main KPIs and a maximum of 3 for all drill KPIs combined. There are three KPI weights in total (OK , Warning , and Critical ), but only Warning and Critical are presented. When checking for identical warnings, both the reason and the weight must be the same across warning levels. This is done not to overflow the user experience. For drills the KPI id is present in the warning message.
